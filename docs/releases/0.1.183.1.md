# ModelPort 0.1.183.1

ModelPort `0.1.183.1` 基于 Sub2API `v0.1.183` 重建，上游基线提交为 `e8cb019fabf8b55199436229044cbf9aa7a82564`。本次重建保留 ModelPort 的产品差异，同时继续继承上游网关、计费、渠道与协议能力。

## 主要内容

- 完整恢复 ModelPort 品牌体系、双版本显示和动态模型港首页。
- 保留免费分组：在已有 usage 记录路径中用户实付/`ActualCost` 为零，余额、订阅金额用量、API Key 金额配额和 user-platform 金额额度不扣减；订阅有效性、用户/分组 RPM、用户并发、鉴权、调度、风控和其他非金额限制仍然执行。沿用现有各模态 usage、`TotalCost`、`account_stats_cost`/账号配额统计记录上游真实成本（含既有账号倍率），不为未落 usage 的路径新增财务台账。仓库没有独立的 per-key RPM。
- 保留即时抽奖、定时开奖、管理配置、事务化幂等结算和用户记录；scheduler 执行错误会写入服务日志。
- 在锁定的 Sub2API `v0.1.183` 基线上恢复指令审核 V2 的采集、判定、复核、统计、可信项和敏感访问能力。该基线内的上游 Prompt Audit 是其唯一运行时配置源，V2 不再提供 per-client supplement。
- Prompt Audit 覆盖所有适用的提示输入网关路由（至少包括 Chat、Responses、Messages、Embeddings、搜索、图片、视频、音频）及现有 HTTP、SSE、WebSocket 链路；无提示路由由清单显式分类并说明理由。Instruction Audit V2 只审核 Responses 的 `instructions` 与 `input[1]` 适用字段，并保持有效非空 `instructions` 优先、否则使用 `input[1]` 的现行选择语义。两条审核链在同一请求或 WebSocket 轮次内各最多执行一次，任一链放行都不会绕过另一条。
- Prompt Audit 当前按既有实现将未脱敏 `full_prompt`（去除 NUL，以 `65536` 个 rune 为截断阈值，超限追加截断标记）写入 `prompt_audit_events` 事件表；staging job 和列表接口仍只使用脱敏元数据，单事件管理详情/API/UI 可以读取该字段，详情路由当前只继承管理端认证。该字段不属于 evidence/hash-raw 密文路径，本版本冻结其现状，不新增加密、删除、脱敏、留存或访问门控变更。历史 OpenSpec/验证材料中“完整提示词不得进入 PostgreSQL、管理 API 或前端”的要求与当前代码/集成测试冲突，已记录为后续独立隐私/产品决策，不应被视为本版本已解决。
- 恢复用户侧 API 密钥连通性测试：使用所选用户 Key 从真实下游网关加载模型，可选择 Chat Completions、Responses 或 Messages 协议以及流式/非流式模式；请求没有专用测试后端或计费旁路，继续经过正常鉴权、调度、usage/计费和服务端权限边界。错误展示会脱敏凭据、上游 URL、账号、渠道和路由信息。
- 将版本发现切换到 `abingooo/modelport` 的四段稳定版本通道。
- 新增 digest 内容寻址的 GHCR 镜像、SBOM、provenance、Cosign 签名、Release 校验和与 digest 固定的宿主更新协议；版本和 SHA 标签采用写入前检查的 best-effort create-only 流程，不宣称 GHCR 标签具备服务端原子不可变性。

## 兼容性

- 支持从旧 ModelPort `custom-v0.1.176.2` 数据库升级，也支持 Sub2API `v0.1.183` 数据库和空数据库初始化。
- 旧 ModelPort 独有迁移仅用于历史 checksum 兼容；新的终态迁移不会重放或重写旧迁移。
- 对旧 ModelPort 已执行的 `188`/`197` 平台扩展，迁移 Runner 会在官方 `224`/`226`/`227` 前验证存量平台值，并用 `236_modelport_legacy_platform_constraints.sql` 保持新旧平台标识超集；不会把 `glm` 静默改名为 `zhipu`。
- public schema 已有业务表但缺少 `schema_migrations` 时会在任何迁移写入前 fail-closed；226 CHECK 兼容预检要求约束已验证、只绑定目标列，并严格匹配单一正向 `IN`/`ANY` 平台集合。
- 用户、余额、订单、订阅、API Key、账号、渠道、用量、抽奖和审核数据不得被删除或静默改名。
- 旧 `instruction_prompt_compat.go` 及其 per-client Prompt Audit supplement 的运行时路由、eligibility provider、管理 API/UI 开关已删除；这是废弃兼容层清理，不删除独立的 Prompt Audit，也不改变 Instruction Audit V2 的严格 Responses 路由边界。
- `prompt_audit_enabled` 在旧 `224_prompt_audit_instruction_patch.sql`、当前 `234_modelport_instruction_audit_bridge.sql` 及 legacy 迁移中仅作为历史 schema/storage、checksum 和存量结构兼容字段保留；当前运行时代码、管理 API/UI 不读取、不写入或据此判定 Prompt Audit。本版本不删除、改名或把该列重新解释为 per-client supplement 配置。
- 指令审核继续使用现有 `TOTP_ENCRYPTION_KEY`、32 字节根密钥、HMAC-SHA256 purpose 派生和 AES-256-GCM；本版本保持现有加密强度，不做升级或降级。指令证据保持原有 evidence 派生路径；哈希原文与 V2 content vault 继续共用原有 hash-raw 派生路径，数据库字段保持原始 BYTEA `nonce || ciphertext || tag`，V2 vault 既有版本字段命名继续原样兼容。purpose、AAD、布局、版本标识、可用性判断和密码学失败语义均不改变。
- 由指令审核/Prompt Audit 配置保存的凭据（Prompt Audit endpoint token、V2 AI 节点 API Key、AI/翻译 token）继续使用现有根密钥直用 AES-256-GCM、无 AAD、标准 Base64 文本(`nonce || ciphertext || tag`)格式和既有失败语义，不改用 evidence/hash-raw 派生路径；各调用方的失效节点排除、fail-closed 或跳过行为保持不变。Redis 中由 SecretEncryptor 加密的短期翻译结果沿用该格式和失败语义，但按 TTL/任务生命周期处理，不作长期跨版本字节不变承诺。本版本不新增上述指令审核/Prompt Audit 密文使用的未经论证的密钥版本分派、历史别名或弱化性解密回退；迁移、上游适配和接口适配不得隐式轮换生产现有密钥、调整任一格式的算法或参数、批量解密或重加密，也不得读时改写、写时转换或版本字段清洗；独立运维轮换须另行授权。必要的结构桥接只能逐字节复制并校验摘要、长度和关联身份；对仍在有效保留期且未被声明生命周期操作删除的既有长期记录，任何适配都不得改写密文字节或 SHA-256 摘要。旧 ModelPort 原有的到期清理、Redis TTL/任务失效以及显式业务操作产生的正常新建、替换或清除按旧路径执行，并验证和记录为预期变化。只有一次性、可丢弃的非生产空数据库或 CI 可沿用上游临时密钥行为；生产初始化必须在首次启动和任何敏感数据写入前配置固定密钥。TOTP、step-up、敏感访问、原文保留、脱敏、日志边界和协议/路由覆盖按独立功能与安全契约验收，不得降低未授权访问防护。

## 安全审计

- 固定版本 `govulncheck v1.7.0` 对 `CGO_ENABLED=0`、`linux/amd64`、`embed` 发布入口源码以及从正式 backend builder 派生、仅省略 `-s -w` 的符号保留诊断二进制均报告 0 个实际可达漏洞。发布工作流会在归一化文件路径后比对两份二进制的完整 Go 版本、模块和构建设置，核对全部运行时分配 ELF 节的地址和大小，并逐字节比较除预期不同的 build-id notes 外所有有文件内容的运行时分配节；诊断二进制不会进入运行镜像或 Release 资产。
- 正式镜像二进制使用 `-s -w`；`govulncheck v1.7.0` 无法从该二进制提取符号，会按其既定逻辑退化为 `go.mod` 精度并保守报告 `GO-2026-6222`、`GO-2026-5932`、`GO-2026-5158`。该退出结果不是从正式二进制恢复出的符号或调用可达性证据，不能表述为二进制扫描为 0，也不能表述为三项实际可达。
- Trivy 的 `CVE-2026-46603` / `GO-2026-6222` 只影响未进入发布依赖闭包的 `x/image/vp8l`；候选闭包中的 `x/image` 仅有 `draw` 与 `math/f64`，头像入口只注册 GIF/JPEG/PNG。该项在 `x/image v0.45.0` 修复，但不为本次锁定的 Sub2API `v0.1.183` 候选扩大依赖差异。
- `GO-2026-5932` 只影响未进入发布依赖闭包的 `x/crypto/openpgp*`，且没有修复版；候选实际使用 bcrypt、curve25519 和 nacl/box。`GO-2026-5158`（OpenTelemetry）同样未进入发布入口调用链。
- 上述模块级发现不构成技术发布阻断，但公开发布前仍需真实安全 owner 留下范围、缓解措施、有效期和批准记录；仓库当前空的 `.github/audit-exceptions.yml` 不代表已批准。
- 正式 Release 会公开 security-owner 批准的 `modelport-go-vex.openvex.json` 与发布时生成的 `modelport-go-module-inventory.json`；前者精确绑定候选提交产品身份，后者记录工作流实际观测到的模块发现集合，两者必须完全对应且不得包含内部敏感信息。

## 更新边界

此 Release 的发布不会连接、更新、重启或回退任何生产实例。GitHub/GHCR 的公开验证完成后，发布流程即停止；`existing_upgrade` 的生产更新、回滚或重启由管理员在完成适用的备份与环境核对后，通过 ModelPort 站内明确确认的人工操作发起；`first_install` 的实际部署及目标冲突预检须以后另行授权。Goal 执行者不得代为点击、调用或部署。

生产只读审计、PostgreSQL/Redis/配置备份、隔离恢复、不变量验证和人工更新边界以
[`MODELPORT_PRODUCTION_UPGRADE_RUNBOOK_CN.md`](../MODELPORT_PRODUCTION_UPGRADE_RUNBOOK_CN.md) 为准。正式发布必须核对 `production_deployment_mode`；仅接受默认的 `existing_upgrade` 或显式选择的 `first_install`。省略输入只能安全回落到 `existing_upgrade` 并满足完整恢复证明，未知模式必须 fail-closed。

`existing_upgrade` 保持真实 PostgreSQL、Redis、持久资产备份和隔离恢复门槛不变；没有真实生产快照的通过报告时，不得声称该模式的生产恢复门槛已经完成。`first_install` 只允许独立受保护的仓库外加密证明断言本次发布不会迁移既有 ModelPort 生产数据集或 ModelPort 所有的 PostgreSQL、Redis、持久资产、部署状态、更新状态；现有恢复证明必须标为 `not_applicable`（`N/A`），绝不能写成 `passed`。干净数据库迁移/幂等性和最终发布镜像 smoke 是该模式的 CI 发布证据，不是生产恢复证据。

所选证明的 SHA-256、记录时间和无末尾换行规范绑定必须与版本、候选提交、上游提交及受保护 GitHub Environment 完全一致；证明不得早于候选提交、位于未来或超过 24 小时。质量、GHCR 写入和 GitHub Release 写入作业都在各自写入前重新校验，重跑不能绕过审批，用户或执行者不能自我批准。Release 只公开 `production-deployment-evidence.json` 中的非敏感绑定字段、固定范围、恢复适用性、CI 证据类型和 `production_update_performed=false`，不上传证明正文、路径、统计、密文或凭据。`first_install` 不声称任何特定服务器或无关服务已被审计或修改；冲突预检属于以后另行授权的实际部署阶段。

宿主更新器、systemd 单元和 ModelPort Compose override 作为校验和覆盖的 Release 资产提供，但不会随容器镜像自动安装或替换。override 让 `/app/data/update-request` 与宿主部署目录中的 `data/update-request` 指向同一绑定目录，并继续让在线更新默认为 `manual`。新镜像默认以 `sub2api` 非 root 用户（UID/GID `1000:1000`）运行；首次使用绑定目录时必须由运维人员预先确认该目录及其文件可由 `1000:1000` 写入。已有旧版目录通常已由旧 entrypoint 完成属主修复；如确需一次性修复，可在维护窗口显式以 root 启动后再恢复默认用户。首次从旧版更新时继续兼容一行四段版本请求；是否安装新的 digest 固定更新器必须由运维人员另行确认。
